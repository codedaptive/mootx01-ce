# Q1 Decision — Provenance Stored as Single Int64 Bitmap

## The question

When provenance is added to drawers (per the 2026-05-08 transcript
reaction), should it be represented as multiple typed columns (one
per axis: source_type, confirmation_state, confidence, channel,
sensitivity), or as a single Int64 bitmap with bit ranges per axis?

## The decision

**Single Int64 bitmap column on the drawer table, named `provenance`.**

This decision applies to drawer-level provenance metadata. Per-rung
model+version tags (a separate concern, addressed in Q2) remain as
typed columns on the `enrichments` table — they capture *which model
produced this representation*, not *how this content entered the
system*.

## Rationale

### 1. Provenance is multi-dimensional and combines

A single drawer can carry combinations like "user-stated AND
user-confirmed AND came-from-Slack." That is not one enum value; it
is three independent axes. Enums force either lossy single-axis
selection or proliferation of combination values. Bitmap bit-ranges
let each axis live independently and compose at query time.

### 2. Matches Simple Machines bitmap doctrine

Locked decision across the Simple Machines product line: no Bool
stored properties on entities, all boolean state lives in Int64
bitmap fields with computed property accessors. GLK ships as a
Simple Machines kit and follows the same pattern. This keeps
cognitive load down across the codebase and aligns with bitmap
philosophy from PalmOS days (pre-allocated bitmap model with open
property bags for the long tail — no migrations).

### 3. SQLite-friendly

Single INTEGER column, indexable, fast bitwise predicates
(`WHERE provenance & ? = ?`). Multiple typed columns would mean
multiple indexes, more migration surface, and JOIN-style filters
when querying across axes.

### 4. Future-proof under reserved bits

The taxonomy below allocates 18 bits and reserves 46. Adding new
source types, channels, or sensitivity levels is a bit-range
allocation, not a schema migration. This is the same payoff bitmap
doctrine delivers across FNode, FSettings, and other Simple Machines
entities.

## Bit layout (Int64)

```
Bits 0–3   source_type        (4 bits = 16 values)
                              0=unknown 1=observed 2=user_stated
                              3=model_inferred 4=external_doc
                              5=instruction 6=imported 7=derived
                              8–15 reserved

Bits 4–6   confirmation       (3 bits = 8 values)
                              0=unconfirmed 1=model_confirmed
                              2=user_confirmed 3=contested
                              4=superseded 5=tombstoned
                              6–7 reserved

Bits 7–9   confidence         (3 bits = 8 values)
                              0=unknown 1=low 2=medium-low
                              3=medium 4=medium-high 5=high
                              6=certain 7=reserved

Bits 10–15 channel            (6 bits = 64 values)
                              0=unknown 1=direct_chat 2=slack
                              3=email 4=teams 5=discord
                              6=matrix 7=telegram 8=whatsapp
                              9=cli 10=api 11=mcp 12=file_import
                              13=web 14=voice 15–63 reserved

Bits 16–17 sensitivity        (2 bits = 4 values)
                              0=normal 1=elevated 2=restricted 3=secret

Bits 18–63 reserved
```

### Definitions

**source_type** — how the content originated, before any review.
- `observed` — captured from a real source (e.g., a tool call result, a parsed document)
- `user_stated` — the user typed or spoke it directly
- `model_inferred` — generated by a model from other content
- `external_doc` — imported from a document not authored in-system
- `instruction` — a directive intended to alter agent behavior (must be flagged so agents don't treat directive language as fact)
- `imported` — bulk-loaded from a non-document external source (e.g., a database export)
- `derived` — computed from other drawers (aggregation, summarization not by a model)

**confirmation** — current validation status.
- `unconfirmed` — captured but not reviewed
- `model_confirmed` — a model reviewed and approved it (lower trust than user)
- `user_confirmed` — the user reviewed and approved it
- `contested` — at least one party flagged it as wrong; corrections in flight
- `superseded` — a later version replaces this one (paired with `supersededBy` in versioning)
- `tombstoned` — explicitly retired; preserved for audit but not surfaced in queries

**confidence** — the system's posterior on the content's correctness.
Categorical, not numeric, to avoid false precision. Models writing
new drawers self-report; user confirmation can override. Used by
the retrieval layer to filter (e.g., "only return high-confidence
facts when the agent is acting on them as instructions").

**channel** — the surface the content arrived on. Matters because
channel rules differ — Slack threading, email replies, mention
semantics, permission scopes. Even when GLK is not the channel
adapter, recording the channel lets downstream agents reason about
where to act.

**sensitivity** — access posture for the content. Composes with the
manifest's estate-level access posture; per-drawer overrides for
content the user marks as restricted within an otherwise normal
estate.

## Schema

```sql
ALTER TABLE drawers ADD COLUMN provenance INTEGER NOT NULL DEFAULT 0;
CREATE INDEX idx_drawers_provenance_source ON drawers (provenance & 0xF);
CREATE INDEX idx_drawers_provenance_confirmation ON drawers ((provenance >> 4) & 0x7);
```

## Swift accessors (illustrative)

```swift
public extension Drawer {
    var sourceType: SourceType {
        SourceType(rawValue: Int(provenance & 0xF)) ?? .unknown
    }

    var confirmation: ConfirmationState {
        ConfirmationState(rawValue: Int((provenance >> 4) & 0x7)) ?? .unconfirmed
    }

    var confidence: Confidence {
        Confidence(rawValue: Int((provenance >> 7) & 0x7)) ?? .unknown
    }

    var channel: Channel {
        Channel(rawValue: Int((provenance >> 10) & 0x3F)) ?? .unknown
    }

    var sensitivity: Sensitivity {
        Sensitivity(rawValue: Int((provenance >> 16) & 0x3)) ?? .normal
    }

    var isUserConfirmed: Bool { confirmation == .userConfirmed }
    var isInstruction: Bool { sourceType == .instruction }
    var isContested: Bool { confirmation == .contested }
}
```

Computed accessors only. No stored Bool properties. Per Simple
Machines doctrine.

## Mutation discipline

Provenance is **mutable on the existing drawer**. A drawer initially
captured as `model_inferred / unconfirmed` becomes
`model_inferred / user_confirmed` when the user approves it. This is
a bit flip on the existing row, not a new drawer.

```swift
// Pattern: clear the field, set the new value
let mask = UInt64(0x7) << 4  // confirmation bits
provenance = (provenance & ~mask) | (newConfirmationValue << 4)
```

This preserves the **rung 1 sacred** rule: confirmation is metadata
about the content, not a change to the content itself. Verbatim
content is never rewritten. The corrections table handles content
changes; the provenance bitmap handles status changes.

## Audit trail for provenance changes

Bitmap captures *current* state. A separate `provenance_audit` table
captures *who flipped which bit when*:

```sql
CREATE TABLE provenance_audit (
    id INTEGER PRIMARY KEY,
    drawer_id TEXT NOT NULL,
    changed_at TEXT NOT NULL,         -- ISO8601
    changed_by TEXT NOT NULL,         -- user_id or model_id
    prior_provenance INTEGER NOT NULL,
    new_provenance INTEGER NOT NULL,
    reason TEXT,                      -- optional free text
    FOREIGN KEY (drawer_id) REFERENCES drawers(rowid)
);
CREATE INDEX idx_provenance_audit_drawer ON provenance_audit (drawer_id);
```

Bitmap = fast queries on current state. Audit table = history of
who flipped which bit when. Both live in the same SQLite file as
drawers (matches Q1-parent decision on manifest storage location).

## What this decision does NOT cover

- **Drawer-level versioning** (lineage_id, supersededBy, corrections
  table) — a separate, already-committed substrate concern.
  Provenance bitmap is the per-version status;
  versioning is the cross-version linkage.
- **Per-rung model+version tags** — Q2 territory. Different axis:
  which model produced *this representation* of the content, vs.
  how the content itself entered the system.
- **Manifest schema specifics** — the parent of Q1. Decision still
  pending; the manifest will carry default provenance posture per
  estate (e.g., "drawers captured via this estate default to
  channel=mcp, source_type=observed").
- **Channel adapter behavior** — out of scope for GLK. Recording
  channel ≠ implementing channel-aware reply logic. Downstream
  applications use channel to route their own behavior.

## Open follow-ups (not blocking)

- Should `confidence` be numeric (0–7 ordinal) or fully categorical
  via enum? Decision: enum-as-ordinal (Confidence: low < mediumLow
  < medium < mediumHigh < high < certain) so comparisons work.
- Should the `channel` taxonomy be locked in v1 or extensible via
  framework profile? Likely framework-profile-extensible, with the
  v1 list as the default.
- How does the retrieval layer use provenance? (e.g., "exclude
  unconfirmed instructions from agent action context"). Belongs in
  the query/retrieval section of the spec, not the schema decision.

## What this decision enables in the publication

- Headline framing: "the runtime is stable, the brain changes" —
  provenance survives model swaps because it's substrate, not
  model-state.
- Theorem 5 (versioning + provenance) gets concrete schema:
  bitmap + audit table + corrections table.
- Theorem 7 (versioning subsumes immutability) is now also
  "provenance subsumes confidence-by-source" — agents reading the
  substrate can filter by source_type and confirmation state
  without trusting any single model's claim about a fact.
- Worked examples in the spec can use provenance bits explicitly:
  "the code review agent ingests PR comments as
  observed/unconfirmed; the architect agent's commentary lands as
  model_inferred/user_confirmed once the user approves."
