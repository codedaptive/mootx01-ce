# ADR-024 — MCP connection ownership, plugin transport, and install-moment dedupe

## Context

MOOTx01 has two install moments that can wire a client's MCP connection:

1. **The CLI installer** (`mootx01 install`, install.sh, Setup app) — places the
   binary, PATH wrappers, and launchd daemon, and merges an MCP entry into each
   detected client config. Transport policy: HTTP to the resident daemon
   (`http://127.0.0.1:4242`) wherever the client schema allows; the native
   proxy subcommand (`mootx01 proxy`) for Claude Desktop, whose schema requires
   a stdio command entry. No client gets a bare `mootx01 serve` stdio entry.

2. **The plugin** (`mootx01@mootx01` for Claude Code, plus the cursor/codex/
   gemini flavors generated by moot-packager) — declarative manifests; as
   shipped through v1.0.14 they wire bare stdio `mootx01 serve`.

The two moments do not know about each other. A user who follows both paths
(the normal fumble-through: brew/installer first, plugin later — or the
reverse) ends up with **two live connections per session to the same estate**,
one of which is a per-session `serve` process holding the estate file directly
while the resident daemon also holds it. That is the single-writer seam: the
architecture (resident-daemon HTTP, ADR-LOOPBACKHTTP-001 posture) exists
precisely so exactly one process writes the estate.

## Decision

### 1. The plugin is the preferred install moment and owns the connection

When the plugin is installed for a client, the plugin's entry is THE
connection for that client. The CLI installer must detect the plugin and
neither create nor keep a competing direct entry.

### 2. Plugin manifests wire HTTP, never bare stdio

The canonical capability entry (`tools/moot-packager/Data/canonical/
capability.json`, EE) changes from `command: mootx01, args: [serve]` to the
loopback HTTP shape (`type: http`, `url: http://127.0.0.1:4242`). The packager
emits the HTTP shape for every plugin flavor whose schema accepts it. Flavors
whose schema cannot express a remote/HTTP server use the proxy bridge
(`command: mootx01, args: [proxy]`) — the same rule the installer already
applies to Claude Desktop. **No shipped manifest may contain a bare
`mootx01 serve` stdio entry.** A `serve` child per session is the defect this
ADR exists to remove.

### 3. Dedupe logic lives in the binary, once

A Claude Code plugin has no install-time script and cannot safely edit a live
client config; the CLI installer is a real program. Therefore the
detect-and-dedupe logic is implemented once, in the mootx01 binary
(MootInstallerCore + Rust port), and invoked from both moments:

- **CLI installer path** (act mode): before wiring a client, detect an
  installed plugin for that client. If present: still install/upgrade the
  binary, PATH wrappers, and daemon (the plugin REQUIRES the binary — a full
  abort would block legitimate upgrades), but **skip writing the direct MCP
  entry, remove any direct entry a previous install wrote**, and state
  plainly: "MOOTx01 plugin already installed — <client> connects through it;
  skipping direct wiring."
- **Plugin session-start hook** (warn mode): detect a competing direct entry
  and warn with its name and location. The hook never edits config.

### 4. Duplicate wiring is fail-loud, and cleanup respects ownership

Any additional `mootx01`-family entry found during the dedupe pass is handled
by ownership, never silently coexisted:

- **Ours, default database** (our server name, no data-dir/estate overrides):
  stale duplicate — replaced or removed.
- **Not ours or non-default** (env overrides pointing at another data dir or
  estate file — e.g. development rigs): reported by name and path, **never
  auto-removed**.

Default-database determination is mechanical: `serve` resolves the default
data dir unless `MOOTX01_DATA_DIR` / `ARIA_MCP_SQLITE_PATH` (or config)
override it, so an entry with no overrides is on the default database by
construction. HTTP entries cannot disagree about the database at all — they
reach whatever estate the daemon holds — which is a further reason transport
defaults to HTTP.

### 5. Version-skew is reported by the daemon, not the installer

At daemon startup (and in `moot_estate_ping` / `moot_estate_status`), when a
plugin is detected, the daemon compares the plugin manifest version against
the binary version and reports skew (e.g. "plugin 1.0.15 expects binary ≥
1.0.15; binary is 1.0.11 — run `mootx01 upgrade`"). Checking at runtime
catches skew from either install order; checking only at install time cannot.

### 6. Development builds carry visible names

Test and development rigs must not exec a binary whose `ps` name is
indistinguishable from the product. Dev/test wrappers and temporary build
artifacts use a suffixed name (`mootx01-dev-<buildnum>` or equivalent argv0)
so rogue instances are self-announcing in a process listing. (Origin: the two
development-rig `serve` processes in the field finding were identifiable only
by their exec paths.)

### Known limitation — plugin manifests are static

Plugin manifests are declarative files stamped at packaging time; they cannot
read runtime configuration. The shipped HTTP entry therefore pins the default
port (`http://127.0.0.1:4242`). A user who overrides the daemon port
(`MOOTX01_HTTP_PORT`) has a plugin that cannot connect until the override is
removed or the manifest is hand-edited; the daemon's ping/status advisory is
the surface that should name this condition. Accepted for the point release;
a config-aware handshake is v1.1 material alongside the multi-database work.

### 7. Deferred to v1.1 (recorded, not designed here)

- **Multiple concurrent moot installations** (two servers/two estates on one
  machine on purpose).
- **Multiple open databases in one session.** The seams exist (GeniusLocusKit
  coordinates N estates; every tool takes `estateID`), but session-level UX
  and config wiring are undesigned. Until then: one daemon, one default
  database, one connection per client.

## Consequences

- The per-session `serve` spawn disappears; sessions share the one daemon and
  its autonomic governor, and telemetry/monitoring see all traffic.
- Exactly one writer holds the estate in every supported configuration.
- Install order (binary-then-plugin or plugin-then-binary) no longer changes
  the outcome: one connection per client, always.
- The plugin becomes inert when the daemon is down (HTTP connect fails)
  instead of silently spawning a private writer. The failure message must
  point at `mootx01 daemon start` / reinstall. This is accepted: an explicit,
  explainable failure beats a hidden second writer.
- Existing installs self-heal on next `mootx01 install`/`upgrade` (act-mode
  dedupe) or surface a warning at next session start (plugin hook).

## Verification

- Installer test matrix covers all four states (plugin present/absent ×
  prior direct entry present/absent) in both ports.
- A live Claude Code session with the updated plugin shows exactly ONE
  mootx01 MCP connection over HTTP, and `ps` shows zero session-spawned
  `mootx01 serve` processes.
- Non-default (override-carrying) entries survive the dedupe pass untouched
  and are named in output.
