## What Was Done

**Part 1: Transport seam** — `CloudKitDatabaseProtocol.swift` + `CloudKitZoneChanges`
mirror. Injectable protocol over CKDatabase (fetch, modifyRecords, fetchZoneChanges,
modifyRecordZones). `CKDatabase` conforms via explicit extension in the same module

`CloudKitZoneChanges` is a constructible mirror of `CKDatabase.RecordZoneChanges`

**Part 2: Slot record mapping** — `SlotRecordMapping.swift`. 15 well-known CKRecords
(`_slot_1`..`_slot_15`, recordType `_ck_device_slot`). Fields: `device_uuid` (String),
`epoch` (Int64 via NSNumber bridge), `last_active_hlc` (Int64 bitPattern of packed UInt64),
`claimed_at` (TEXT ISO8601). `populate(record:from:)` mutates an existing record in place
to preserve its change tag for CAS evictions.

**Part 3: Claim operation** — `SlotClaimOperation.swift`. Fetches all 15 slot records,
builds `SlotTable` snapshot, runs `claimSlot(for:preferring:now:)`. Free slots: create new
CKRecord + CAS save. Eviction: take fetched record (with change tag), bump epoch, populate
in place, CAS save. CAS race loss → jittered exponential backoff (`min(0.1 * 2^(n-1), 5.0)
* (0.5 + 0.5 * rng())`). After `maxAttempts` → `slotExhausted`. All injected (database,
rng, clock, sleep) for deterministic tests.

**Part 4: Epoch fence** — `EpochFence.swift`. Fetches this device's slot record,
compares registry epoch to stored identity epoch. Mismatch → `reenrollRequired(slot:
staleEpoch:currentEpoch:)` BEFORE any outbox read. Heartbeat: updates `last_active_hlc`
via CAS save (`.ifServerRecordUnchanged`). CAS failure on heartbeat also triggers
`reenrollRequired` (conservative: assume eviction).

**Part 5: OutboxStore.remintAll** — Added to `OutboxStore.swift`. Reads all pending
outbox entries in ascending HLC order, deletes each, mints a fresh HLC under `newNodeID`,
reinserts. Safe because outbox entries are unpushed local state — LWW has no prior
decisions against these HLCs.

## Discoveries

### HLC physicalTime 40-bit overflow in 2026

The HLC packed format stores physicalTime in 40 bits. Current Unix time in milliseconds
(~1.75 trillion in 2026) exceeds `2^40 = 1.099 trillion`. When a recently-generated HLC
is packed and decoded via `HLC(packed:)`, the recovered `physicalTime` is the truncated
40-bit value (~652 billion ms ≈ year 1990). `SlotTable.evictionCandidate` compares
decoded `physicalTime` against current `nowMillis` (full 64-bit), yielding a ~35-year
apparent inactivity for every stored HLC.

**Impact in production:** Any heartbeat HLC stored in CloudKit and decoded by the
eviction check appears far beyond `SlotLongInactivityWindow (30 days)`. This means
ALL slotted devices will ALWAYS appear eviction-eligible after any heartbeat is stored
and read back.

**Workaround in this mission:** Tests use `lastActiveHLC: HLC.zero` + recent `claimedAt`
to make slots "not evictable" (ghost-window path: excluded from long-inactivity check
when claimedAt is recent, not a ghost because <1 hour old).

**This is a pre-existing design issue that must be resolved in a follow-up mission
before the slot registry is production-safe.** The 40-bit physical time field needs
to be extended, or `SlotTable.evictionCandidate` needs to compare truncated values
consistently (i.e., truncate `nowMillis` to 40 bits before comparison), or the
inactivity window needs to be based on `last_active_at` (a separate TEXT ISO8601 field)
rather than the HLC's physical time.

Recommended fix (non-breaking): compare `(nowMillis & 0xFF_FFFF_FFFF) - physicalTime`
in the eviction window check, so both sides are 40-bit. This is consistent since the
HLC generator also uses `& 0xFF_FFFF_FFFF` when packing.

### CKDatabase.fetch bridge pattern

`CKDatabase.fetch(withRecordIDs:desiredKeys:)` is callback-only in this SDK version.
Bridged via `withCheckedThrowingContinuation`. CKRecord integer fields must be read
via `as? NSNumber` then `.int64Value`, NOT directly as `as? Int64` — though in practice
both work in this context, the `NSNumber` pattern is what the existing `CKRecordMapping`
uses and is more defensive.

### FakeCloudKitDatabase CAS model

Object-identity CAS works reliably for the test cases: SlotClaimOperation's eviction
path takes the exact fetched CKRecord instance (mutation in place) → passes the identity
check. The race test works because actor serialization ensures the second caller's fresh
CKRecord instance has a different identity than the first caller's stored instance.
