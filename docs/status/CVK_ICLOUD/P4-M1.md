## Discoveries

### UUID→text CKRecord round-trip

`CKRecordMapping.assign(.uuid(u))` stores `u.uuidString as NSString`. `typedValue(from:)` decodes NSString back as `.text(s)`, not `.uuid(u)`. This means:

- **Locally-written rows**: `id: .uuid(sharedID)` (PersistenceKit stores the TypedValue as written)
- **Pulled rows**: `id: .text(sharedID.uuidString)` (CKRecord encoding loss)

Consequences:
1. `upsertSync(conflictColumns: ["id"])` compares `.uuid(x)` against `.text(x.uuidString)` — not equal in `InMemoryStateActor.upsertRow`, so pulled rows INSERT instead of UPDATE. Locally-written row and pulled copy coexist as separate rows.
2. `applyInbound`'s tombstone delete predicate uses `.uuid(decoded.rowKey)`. Pulled rows (stored as `.text`) are not matched — delete silently fails. However, `writeTombstoneHLC` is unconditional, so sync-meta always correctly records is_deleted=1.
3. The LWW gate (`readSyncHLC`) uses sync-meta, not the user table. It correctly blocks stale resurrects regardless of the user-table duplicate-row situation.

**Mitigations in harness** (test-only, not Sources/):
- `queryA/queryB` try `.text(id.uuidString)` first, fall back to `.uuid(id)`. This finds both locally-written and pulled rows, and prefers the pulled version (which is what scenario (b) LWW and (f) test).
- Scenario (e) assertions are sync-meta based, not user-table based, because the tombstone delete predicate cannot reach the `.text` row.

**Implications for P4-M2/M3**: The underlying round-trip loss is in `CKRecordMapping.typedValue(from:)` — it should try `UUID(uuidString:)` before returning `.text`. This is a Sources/ fix. If P4-M2 or P4-M3 require reliable user-table presence/absence checks for deleted rows, that fix should be scoped into that mission.

### Poll-deadline pattern works cleanly

No `Task.sleep` anywhere in the harness. The `ContinuousClock.now < deadline` + `Task.yield()` pattern reliably waits for outbox growth (observer fires after upsert). Zero flakiness across 3 runs.

### Slot claim correctness at setUp() time

Both engines race through SlotClaimOperation against the same CloudZoneFake. CAS via ObjectIdentifier semantics in `modifyRecords(.ifServerRecordUnchanged)` correctly arbitrates, giving each engine a distinct slot.
