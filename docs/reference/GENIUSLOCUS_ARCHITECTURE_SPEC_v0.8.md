# GeniusLocus Architecture Specification — v0.8

## 1. Purpose, audience, and scope

### 1.1 Purpose

This specification defines the GeniusLocus architecture: the data structures, operations, rules, and conformance requirements that any implementation must satisfy. It is a contract. It does not argue why the architecture is shaped as it is; that work lives in `GENIUSLOCUS_THESIS_RFC.md`. It does not plan implementation milestones; that work lives in `GENIUSLOCUS_IMPLEMENTATION_PLAN_v0.XX.md`. It does not enumerate open questions; those live in `OPEN_QUESTIONS_FOR_REFINEMENT.md`.

### 1.2 Audience

Implementers writing code against the architecture. Reviewers verifying that an implementation conforms. Test authors writing conformance fixtures. Future spec editors evolving the architecture.

### 1.3 Scope

In scope: the storage tiers, bitmap layouts, action verbs, adjective system, lattice citation rules, manifest schema, audit-trail semantics, standing-signals operational model, error modes, security and provenance rules, extensibility mechanisms, and conformance requirements that define a GeniusLocus.

Out of scope: any specific application built atop GeniusLocusKit (Fulcrum, AI Brain, repo-craft); any specific tiny-model architecture trained against a GeniusLocus; any specific user interface; any specific access surface (ARIA_MCP, the MCP server) beyond noting that an access surface composes GeniusLoci and is not the substrate's concern.

## 2. Definitions and terminology

| Term | Definition |
|---|---|
| **GeniusLocus** | A self-contained semantic-plus-vector database holding durable memory for AI agents and human applications. Singular: a GeniusLocus. Plural: GeniusLoci. |
| **Estate** | One instance of a GeniusLocus. Identified by `estate_uuid`. |
| **Wing** | A top-level organizational container within an estate. Wings group rooms by domain. |
| **Room** | A second-level organizational container within a wing. Rooms group drawers by topic. |
| **Drawer** | The primary content row. Holds verbatim user content plus its rungs. |
| **Tunnel** | A directional or bidirectional relationship between two drawers. Has a `kind`. |
| **KGFact** | A subject-predicate-object triple extracted from drawer content. Constitutes rung 1.5. |
| **Vector** | A dense embedding of drawer content, model-and-version tagged. Constitutes rung 3. |
| **DiaryEntry** | A chronological row recording substrate-level events. |
| **Proposal** | A candidate state change generated by the substrate, awaiting confirmation. |
| **Association** | A weighted edge between two objects in the substrate, accumulated by the dreaming daemon. |
| **LearnedReference** | A canonical external reference brought into the substrate via the `learn` verb. |
| **Manifest** | A self-describing key-value table within an estate that declares estate-level configuration. |
| **Substrate** | The complete data layer of an estate: bitmap tier + structured-row tier + blob tier + audit log + manifest. |
| **Verb** | One of nine action operations the substrate supports. |
| **Adjective** | A cross-noun structural attribute. There are four: state, trust, sensitivity, exportability. |
| **Bitmap** | An Int64 column carrying packed structural attributes. Three per row: adjective, operational, provenance. |
| **Lattice anchor** | A drawer's position on the universal coordinate system: a UDC code plus an optional Wikidata Q-ID. |
| **Lattice footprint** | The OR-reduction of every row's lattice anchor across an estate. Computed, not declared. |
| **Standing signal** | A long-running observer that detects deltas and emits proposals, associations, mutate-candidates, or diagnostic reports. |
| **Audit row** | An immutable record of a bitmap mutation. Append-only. |
| **Rung** | One of six representational forms of a drawer's content (verbatim, KG, précis, vector, theme, lane). |

## 3. Architectural principles and invariants

The following invariants hold for every conforming GeniusLocus. An implementation that violates any of them is non-conforming.

**I-1. Verbatim rung is immutable.** Rung 1 (verbatim user content) is never mutated after capture. Corrections produce new versions linked by `lineage_id`; the original is preserved.

**I-2. All bitmap mutations write audit rows.** Every change to any of the three Int64 bitmap columns of any row writes an immutable audit row recording timestamp, actor, before-bitmap, after-bitmap, reason. The audit table is append-only.

**I-3. The substrate accepts no `secret + public` combination.** The verb layer rejects any `mutate` or `capture` call that would produce a row with `sensitivity = secret` AND `exportability = public`. The maintenance daemon scans for the combination periodically and emits a discipline-violation proposal if one is detected.

**I-4. Every model-generated rung carries `model_id` and `model_version`.** Précis (rung 2), vector (rung 3), theme (rung 4), and any future model-generated rung must record the identifier and version of the model that produced them.

**I-5. Every drawer carries a lattice anchor.** Every drawer has a UDC code at minimum. Wikidata Q-ID is optional but recommended; when absent it is populated by the enrichment daemon.

**I-6. Audit rows can be tombstoned but not modified.** Only the `expunge` verb may tombstone an audit row. Tombstoned audit rows preserve the fact-of-tombstoning. No other operation touches audit rows.

**I-7. The verb count is fixed at nine.** New domain operations compose the existing verbs rather than adding new ones. The verb count and the verb names are part of the contract.

**I-8. The adjective category count is fixed at four.** State, trust, sensitivity, exportability. New structural attributes extend existing categories or live in the operational bitmap, not as new adjective categories.

**I-9. Field width is 4 bits in the bitmap tier.** Adjective fields and most operational fields are 4 bits wide, admitting 16 values per field. The state field is the one category at realistic risk of growing beyond 16 values; it carries an extension mechanism (§ 10.1). Other adjective categories (sensitivity, exportability, trust) and operational fields use far less than their 16-value capacity at v1 and have no extension mechanism; categories that exhaust their capacity in a future spec version produce a successor architecture per § 10.4.

**I-10. Every bitmap field reserves at least 30% growth space.** No field uses all 16 of its values at v1. Growth headroom is preserved at the high end of each field's value range.

**I-11. Bitmap layouts within a published version are stable.** Once a bitmap layout is published in a versioned manifest, the layout is not mutated. New layouts produce new manifest versions; old data is readable via the manifest's `bitmap_layout_version` value.

**I-12. The substrate provides storage; applications do not bring their own.** GeniusLocusKit composes LocusKit (content, KG), VectorKit (vectors), and CorpusKit (RAG content-plus-vectors). The application calls verbs against the kit; the kit owns the database files.

**I-13. Federation is not a substrate concern.** Multi-estate operation is mediated by a separate access surface (ARIA_MCP). The substrate does not communicate with other substrates.

**I-14. Provenance is set at write and mutated only via the audit-recorded path.** `capture`, `propose`, `learn`, and `associate` set the provenance bitmap at write time. Subsequent mutations go through `mutate_bitmap`, which writes an audit row.

## 4. System model: nouns, verbs, flows

Every kit-API call is one verb applied to a noun, optionally constrained by adjectives. The noun is the data, the verb is the action on it, and the adjectives narrow the result. The verb count is fixed at nine and the adjective category count at four (invariants I-7, I-8); new domain operations compose existing verbs rather than extending the vocabulary. The full grammar is set out in `ARIA_LEXICON.md`.

### 4.1 Nouns

The substrate's noun set is fixed at v1:

| Noun | Category | Storage | Description |
|---|---|---|---|
| Drawer | content | content DB | Primary verbatim content plus six rungs |
| Tunnel | structure | content DB | Drawer-to-drawer relationship with kind |
| KGFact | structure | content DB | Subject-predicate-object triple (rung 1.5) |
| Vector | content | vectors DB | Dense embedding of drawer content (rung 3) |
| DiaryEntry | structure | content DB | Chronological substrate event |
| Proposal | derived | content DB | Candidate state awaiting confirmation |
| Association | derived | content DB | Weighted edge between two objects |
| LearnedReference | reference | content DB | Canonical external reference grounded by `learn` |

Each noun publishes the set of verbs it accepts (§ 9.1).

### 4.2 Verbs

The substrate exposes nine action verbs:

| Verb | Flow | What it does | Default adjectives at output |
|---|---|---|---|
| `capture` | caller-driven | Bring user content into the substrate as a verbatim row | trust=verbatim, state=active |
| `reanchor` | caller-driven | Change where existing content sits in structure (room, wing, lattice anchor) without changing identity | preserves all |
| `mutate` | caller-driven | Change structural state of an existing row | varies; cascades by design |
| `withdraw` | caller-driven | Retire from active circulation, preserve history | state=withdrawn |
| `expunge` | caller-driven, irreversible | Hard-erase including audit | state=tombstoned (audit also tombstoned) |
| `recall` | caller-driven | Read content back, by any criteria the kit exposes | preserves |
| `propose` | substrate-driven | Generate candidate state, awaiting confirmation | trust=proposed, state=pending |
| `associate` | substrate-driven | Accumulate connective weight between objects | trust=derived |
| `learn` | grounding-driven | Ingest canonical external reference | trust=canonical, state=active |

### 4.3 Three flows

Verbs partition into three flows by who initiates them:

- **Caller-driven flow:** `capture`, `reanchor`, `mutate`, `withdraw`, `recall`, `expunge`. The application invokes these synchronously.
- **Substrate-driven flow:** `associate`, `propose`. Standing signals (§ 13) emit these. The application does not invoke them directly.
- **Grounding-driven flow:** `learn`. The application brings authoritative external reference into the substrate.

### 4.4 Three content origin classes

Every row is in exactly one content origin class, determined by which verb produced it:

- **User content** — produced by `capture`, mutated by `mutate`, retired by `withdraw`. Default trust: `verbatim`.
- **Substrate-derived content** — produced by `associate` or `propose`. Default trust: `derived` (associations) or `proposed` (proposals).
- **Reference content** — produced by `learn`. Default trust: `canonical`.

`mutate` may promote a row across classes (e.g., a confirmed proposal becomes derived or verbatim).

## 5. Data model

### 5.1 Three storage tiers

Every row in the substrate exists in three tiers simultaneously:

| Tier | Storage | Holds | Read discipline |
|---|---|---|---|
| Bitmap tier | Three Int64 columns per row | Small-finite enums (≤16 values per field, not application-extensible) | SIMD-parallel filter |
| Structured-row tier | Variable-width columns | Timestamps, foreign keys, counters, lengths | Relational (joins, aggregates) |
| Blob/JSON tier | TEXT or BLOB columns | Open-ended payloads (verbatim content, payloads, vector data) | Mined later by dreaming daemon |

### 5.2 Three encoding patterns

Bitmap-tier fields use one of three patterns chosen by category type:

- **Exclusive-deterministic** — Contiguous integers, no gaps. Used where a row is in exactly one value and values are discrete-and-named. Examples: state (within cluster), trust, mode, source, proposal_kind, target_object_type, capture_channel, content_kind, arity. Mask stability: equality queries forever.
- **On-a-scale** — Spaced integers with gaps for future intermediate insertions. Used where values position on an ordered continuum. Examples: sensitivity, exportability, refresh_policy, decay_class, drift_severity, confidence. Mask stability: ordering queries forever.
- **Non-exclusive set (bitset)** — One bit per value. Used where a row can have multiple values simultaneously. Examples: signal_sources_seen, feature_flags. Mask stability: equality and subset queries forever.

(Note: state is contiguous within each of its three clusters but arranged across clusters at threshold boundaries, making it gradient-ordered overall.)

### 5.3 Three adjacency types

Fields are grouped within bitmaps by adjacency type so that adjacency-typed masks are dense ranges:

- **Temporal adjacency** — Sharing a phase or cycle of the substrate's clock (state, refresh_policy, drift_severity, decay_class).
- **Spatial adjacency** — Sharing a structural zone (sensitivity, exportability, mode, proposal_kind, target_object_type, arity).
- **Empirical adjacency** — Sharing an evidence class or content shape (trust, source, confirmation_source, generated_by_class, capture_channel, content_kind, feature_flags, signal_sources_seen).

The most-frequently-filtered adjacency cluster sits at the low bits of each bitmap.

### 5.4 Three Int64 bitmap columns per row

Every substrate row carries three Int64 columns:

- **Adjective bitmap** — cross-noun uniform layout (§ 5.5).
- **Operational bitmap** — per-noun layout (§ 5.6).
- **Provenance bitmap** — Q1-locked layout (§ 5.7).

Total: 192 bits per row, 24 bytes. A million rows fits in 24 MB.

### 5.5 Adjective bitmap layout

```
adjective_bitmap (Int64), low-to-high:
  Bits 0–3   (4 bits): State          [temporal,  gradient]
                       0=active 1=pending 2=contested
                       3=superseded 4=decayed 5=withdrawn 6=expired
                       7=rejected 8=accepted 9=tombstoned
                       10–15 reserved (37.5% growth)

  Bits 4–7   (4 bits): Sensitivity    [spatial,   scale-gapped]
                       0=normal  4=elevated  8=restricted  12=secret
                       1–3, 5–7, 9–11, 13–15 reserved

  Bits 8–11  (4 bits): Exportability  [spatial,   scale-gapped]
                       0=private  8=public
                       1–7, 9–15 reserved

  Bits 12–15 (4 bits): Trust          [empirical, gradient]
                       0=verbatim 1=observed 2=imported
                       3=canonical 4=derived 5=proposed
                       6–15 reserved (62.5% growth)

  Bit  16    (1 bit):  State-extension flag

  Bits 17–63 (47 bits): RESERVED for cross-noun adjective category growth
```

17 bits used, 47 reserved.

### 5.8 Lattice anchor

Every drawer carries a lattice anchor:

- `udc_code` — TEXT, required. The drawer's depth-coordinate classification code (see "Two schemes, two field names" below). Empty string is the no-anchor sentinel.
- `udc_facets` — TEXT, optional. Comma-separated additional facet codes.
- `wikidata_qid` — TEXT, optional but recommended. Wikidata Q-ID (e.g., `Q11165`).
- `wikidata_qids_secondary` — TEXT, optional. Comma-separated additional Q-IDs.

When `wikidata_qid` is absent at capture, the enrichment daemon populates it. When the daemon cannot resolve a Q-ID, the field remains NULL and the drawer is included in a periodic resolution sweep.

The estate's lattice footprint is the OR-reduction of every row's anchor, computed on demand. Footprint is observed; no application or user pre-declares it.

#### Two schemes, two field names

The depth coordinate is currently carried under **two different field
names in two different layers**, and they hold codes from **two
different classification schemes**. A reader wiring the two layers
together must not mistake one for the other — both are `String` (Swift)
/ TEXT (SQLite), so the compiler will not catch a code from one scheme
fed into the other layer's field.

| Layer | Field name | Type | Scheme it carries |
|---|---|---|---|
| Storage / wire (LocusKit `Drawer`, SQLite column) | `udc_code` (Swift `udcCode`) | `String` / TEXT | The persisted depth code. Named for UDC for historical reasons; it stores whatever depth code the capture path supplies, which in the shipped system is an MDCC code. |
| Reasoning (EideticLib / NeuronKit `LatticeAnchorInference`) | `mdccCode` | `String` | The live MDCC code resolved by the deterministic linguistic pipeline. |

**MDCC (MOOT Decimal Classification) is the shipped reference scheme.**
UDC was the originally specified scheme and the source of the
`udc_code` field name, but MDCC-03 retired the UDC schedule in the
reasoning layer and named the resolver's output `mdccCode`. UDC is no
longer populated; see `DECISION_LATTICE_CITATION_UDC_WIKIDATA_2026-05-07.md` for the
original decision and `MDCC_ANNEX_SPEC_v0.1.md` for the MDCC scheme. MDCC is
an original, openly licensed decimal scheme with the same depth-coordinate
mental model, so the `udc_code` storage field keeps its shape while its
contents are now MDCC codes.

The two field names coexist deliberately: MDCC-03 renamed the
reasoning-layer field but left the storage/wire field as a separate
symbol (`udc_code`) to avoid a schema migration. Renaming the storage
field to `mdcc_code` is a separate future migration; until it lands,
treat `udc_code` (storage) and `mdccCode` (reasoning) as the **same
depth coordinate under two names**, both `String`, neither
compiler-policed against the other.

### 5.9 Manifest schema

The manifest is a key-value table within the estate's primary database. The schema is locked by `DECISION_Q1_MANIFEST_SCHEMA_2026-05-08.md`. v1 required keys:

```
manifest_version          string   semantic version of the manifest schema
schema_version            string   semantic version of the storage schema
estate_uuid               string   UUIDv4 identifying this estate
estate_name               string   human-readable name
owner_identifier          string   iCloud-account-keyed owner ID
lattice_citation          string   e.g., "UDC:2024+Wikidata:2024-Q3"
framework_profile         string   profile name and version (application bookkeeping)
framework_profile_definition  JSON  application-supplied configuration values
zoom_window_low           integer  optional UDC depth low end (hint, not enforced)
zoom_window_high          integer  optional UDC depth high end (hint, not enforced)
access_posture            integer  estate-level access defaults (bitmap)
provenance_defaults       integer  default provenance bits applied to new drawers
active_storage_mode       integer  current L/Q/P configuration (bitmap)
tables_present            string   comma-separated list of optional tables present
created_at                string   ISO8601 timestamp
last_modified             string   ISO8601 timestamp
bitmap_layout_version     string   "v0.35" — adjective bitmap layout version
provenance_bitmap_version string   "v1.0" — provenance bitmap layout version
```

v1 optional keys:

```
federation_group_id            string   federation membership; NULL if standalone
mining_patterns_hash           string   hash of active mining patterns
tiny_model_id                  string   identifier of per-estate trained model
tiny_model_training_corpus_size integer rows used in most recent training run
operational_bitmap_layouts     JSON     map of noun-name to layout spec
```

The manifest is authoritative for the estate. A reader with the spec and the manifest can interpret the estate without out-of-band information.

| `audit_id` | INTEGER monotonic | per-estate | substrate at audit-row creation |
| `udc_code` | string | universal | external (UDC consortium) |
| `wikidata_qid` | string `Q\d+` | universal | external (Wikidata) |

## 6. Behavioral semantics

### 6.1 State-cluster topology

The state field of the adjective bitmap takes ten values partitioned into three clusters at integer thresholds 3 and 7.

| Cluster | Values | State range | Semantic |
|---|---|---|---|
| Know-now | active (0), pending (1), contested (2) | `state < 3` | What we currently believe |
| Knew-past | superseded (3), decayed (4), withdrawn (5), expired (6) | `3 ≤ state < 7` | What we used to believe |
| Terminal | rejected (7), accepted (8), tombstoned (9) | `state ≥ 7` | What we know once and have erased or finalized |

Three queries are first-class, each compiling to a single threshold-compare:

- *Currently believe X?* → `(adj >> 0) & 0xF < 3`
- *Used to believe X?* → `((adj >> 0) & 0xF) >= 3 AND ((adj >> 0) & 0xF) < 7`
- *Knew once and erased/finalized?* → `(adj >> 0) & 0xF >= 7`

### 6.2 State transitions

Legal state transitions form a directed graph. Each transition is initiated by a specific verb.

| From | To | Initiated by | Notes |
|---|---|---|---|
| (none) | active | `capture` | New user content. |
| (none) | pending | `propose` | New substrate-derived candidate. |
| (none) | active | `learn` | New canonical reference. |
| pending | active | `mutate` (kind=confirm) | Proposal accepted. |
| pending | rejected | `mutate` (kind=reject) | Proposal declined. |
| active | contested | `mutate` (kind=contest) | Disagreement flagged. |
| contested | active | `mutate` (kind=resolve) | Disagreement resolved in favor of this row. |
| contested | superseded | `mutate` (kind=supersede) | Disagreement resolved against this row. |
| active | superseded | `capture` of correction with `lineage_id` match | Newer version of same lineage. |
| active | decayed | maintenance daemon | Auto-fade through inattention. |
| active | withdrawn | `withdraw` | User suppression. |
| active | expired | maintenance daemon | Aged out per policy. |
| {decayed, withdrawn, expired, superseded} | active | `mutate` (kind=revive) | Reactivation. |
| any state | accepted | `mutate` (kind=accept) | Terminal confirmation. |
| any state | tombstoned | `expunge` | Hard erasure. Audit also tombstoned. |

Illegal transitions are rejected with `DisciplineViolation` (§ 10).

### 6.3 Mutation cascade rules

Certain mutations cascade across linked rows.

- A `mutate(kind=supersede)` on row A creates a `supersedes` tunnel from a successor row B to A and sets A's state to superseded.
- An `expunge` on row A also expunges all tunnels with A as source or target, and tombstones all audit rows referencing A.
- A `mutate(kind=confirm)` on a Proposal row promotes it to `state=active` AND creates the proposed object (drawer, tunnel, KGFact, etc.) in its target_object_type.
- A `withdraw` on row A does not cascade to tunnels referencing A; tunnels remain queryable as part of the historical structure.

### 6.4 Trust ordering and the trust threshold

Trust values are ordered by AI relevance: low values are highly served by default; high values are often filtered out.

| Value | Name | Meaning | Default-served by AI? |
|---|---|---|---|
| 0 | verbatim | Directly stated by user | yes |
| 1 | observed | Sensor or stream capture | yes |
| 2 | imported | From a trusted federation peer | yes |
| 3 | canonical | Authoritative external reference | yes |
| 4 | derived | Substrate-computed | requires confirmation |
| 5 | proposed | System-generated candidate | requires confirmation |

The threshold `trust < 4` separates trustworthy-for-action content from content requiring confirmation. Recall calls without explicit `trust` filter default to `trust < 4`.

### 6.5 Sensitivity tiers

| Value | Name | Access requirement |
|---|---|---|
| 0 | normal | default-visible to estate owner |
| 4 | elevated | requires elevated access claim |
| 8 | restricted | requires explicit grant |
| 12 | secret | requires fresh-auth, single-row access |

Sensitivity values 1–3, 5–7, 9–11, 13–15 are reserved for future intermediate tiers.

### 6.6 Forbidden combinations

The verb layer rejects:

- `sensitivity = secret` (12) AND `exportability = public` (8). Rejected with `DisciplineViolation`. Storage layer can represent the combination; verb layer must not allow it.

Additional forbidden combinations may be added in future spec versions; existing forbidden combinations are constitutional.

### 6.7 Lattice footprint computation

The estate's lattice footprint is the union of every drawer's lattice anchor, expressed as:

- A set of UDC code prefixes (computed from the unique UDC codes present, collapsed to common prefixes).
- A set of Wikidata Q-IDs (the unique Q-IDs present plus any of their parent classes via `instance of` / `subclass of` traversal up to a configurable depth).

The footprint is computed on demand by the kit's `estate.lattice_footprint()` call. It is not cached as a manifest value; it changes with every capture or expunge.

### 6.8 Audit-trail recovery semantics

Given the audit log, the substrate reconstructs any row's historical bitmap state at any timestamp:

```
state_at(row_id, timestamp) =
  initial_bitmap(row_id) XOR XOR_of_all_mutation_deltas(row_id, t ≤ timestamp)
```

The `recall(at: timestamp)` form returns rows as they were at the supplied timestamp. Tombstoned rows are visible at timestamps before their tombstoning; absent at timestamps after.

| Noun | Accepts |
|---|---|

### 7.3 Hydration levels for `recall`

`recall` accepts a `hydration_level` parameter:

| Level | Returns | Cost |
|---|---|---|
| `bitmap` | three Int64 bitmap columns only | cheapest |
| `structured` | bitmap + structured-row tier | typical (default) |
| `blob` | bitmap + structured + blob/JSON tier | hydrates content |
| `full` | bitmap + structured + blob + computed enrichments + matrix-layer derived fields | most expensive |

### 7.4 Synchronous vs asynchronous

Caller-driven verbs are synchronous: the kit returns when the operation completes. `recall` returns a paged stream; the first page is synchronous.

Substrate-driven verbs (`associate`, `propose`) are emitted by standing signals (§ 13) asynchronously. The application does not invoke them and does not wait for them.

`learn` is synchronous at registration time and asynchronous at validation time (the byReference validation signal polls byReference sources on its schedule).

### 7.5 Atomicity

All single-call operations are atomic at the row level. The substrate guarantees that a row's bitmap update either succeeds completely or fails completely; no partial bitmap updates are visible to readers.

Multi-row operations are not atomic at the multi-row level by default. Callers wanting multi-row atomicity must wrap their calls in an explicit transaction.

### 7.6 Idempotency

| Verb | Idempotent? |
|---|---|
| `capture` | no (every call produces a new row) |
| `reanchor` | yes |
| `mutate` | yes if supplied with explicit prior bitmap state (conditional mutation) |
| `withdraw` | yes |
| `expunge` | yes |
| `recall` | yes |
| `propose` | substrate-emitted |
| `associate` | substrate-emitted |
| `learn` | yes (re-registration is no-op if source+handle match) |

### 7.7 Five operator primitives

The recall engine exposes five operations as first-class primitives:

| Operator | What it does | Cost per row |
|---|---|---|
| AND-with-mask | field equality on contiguous fields | 1 instruction |
| Threshold-compare | cluster membership on gradient-ordered fields | 1 instruction (after AND-mask) |
| XOR | identity, per-field change detection, Hamming distance | 1 XOR + 1 popcount |
| Shift-extract | field value as integer | 1 instruction |
| SIMD-ballot / parallel reduction | per-row boolean results to compact output | 1 ballot + 1 popcount/ctz per batch |

Higher-level filter handles compile to short sequences of these primitives.

#### 7.8.8 Method-level invariants

For every kit-published method:

### 7.9 Bitmap evaluator

The bitmap evaluator compiles a `RecallFrame.filterChain` into a sequence of operator primitives (§ 7.7) and executes that sequence against the estate's rows. This section defines the contract that every conforming evaluator must satisfy. Two conforming evaluators given the same estate and the same `RecallFrame` produce equivalent results.

**The bitmap layouts in §§ 5.5–5.7 — field positions, bit widths, threshold values, masks — are implementation concerns of the evaluator. They are not part of the kit's public surface. Callers express intent through the named `Filter` cases below; the evaluator translates that intent into the bitmap operations the storage tier needs. A caller never writes `state < 3` or `trust < 4` or extracts a 4-bit field directly. The integers and thresholds live inside the evaluator.**

#### 7.9.1 Filter algebra

A `Filter` is one of:

```swift
public indirect enum Filter {
    // State queries (named, not numeric)
    case currentlyBelieve            // state-cluster know-now
    case usedToBelieve               // state-cluster knew-past
    case knewOnceAndErased           // state-cluster terminal
    case state(State)                // exact state value, e.g. .active, .contested
    case stateInCluster(StateCluster)

    // Trust queries
    case trustworthy                 // default-served trust threshold
    case requiresConfirmation        // trust above threshold
    case trust(Trust)                // exact trust value, e.g. .verbatim, .canonical
    case trustAtMost(Trust)

    // Sensitivity queries
    case sensitivity(Sensitivity)    // exact sensitivity value
    case sensitivityAtMost(Sensitivity)

    // Exportability queries
    case exportable                  // exportability == public
    case private_                    // exportability == private

    // Provenance queries
    case userConfirmed               // confirmation ≥ user_confirmed
    case modelConfirmedOnly          // confirmation == model_confirmed (excludes user_confirmed)
    case unconfirmed                 // confirmation == unconfirmed
    case sourceType(SourceType)
    case channel(ProvenanceChannel)
    case confidenceAtLeast(Confidence)

    // Operational queries (per-noun, named)
    case captureChannel(CaptureChannel)
    case contentKind(ContentKind)
    case hasFeatureFlag(FeatureFlag)
    case proposalKind(ProposalKind)
    case targetObjectType(TargetObjectType)
    case associationSignalSource(AssociationSignalSource)
    case decayClass(DecayClass)
    case refreshPolicy(RefreshPolicy)
    case driftSeverity(DriftSeverity)
    case learnMode(LearnMode)
    case sourceCatalogEntry(SourceCatalogEntry)

    // Structural queries
    case inRoom(RoomID)
    case inWing(WingID)
    case lineageID(LineageID)
    case createdAfter(Date)
    case createdBefore(Date)
    case latticeAnchor(LatticeAnchor)
    case latticeUnder(udcPrefix: String)
    case wikidataConcept(WikidataQID)

    // Content queries
    case contentMatches(String)
    case nearVector(Vector, count: Int)

    // Composition
    case all([Filter])     // AND
    case any([Filter])     // OR
    case not(Filter)
}
```

No case takes a raw bit position, mask, or threshold integer. Every case is either a named enum value (`.active`, `.verbatim`, `.elevated`) or a domain-meaningful argument (a date, a room ID, a vector). The integers from §§ 5.5–5.7 are the evaluator's private translation table, not the caller's vocabulary.

A `RecallFrame.filterChain` is a `[Filter]` interpreted as `Filter.all(filterChain)` — implicit conjunction at the top level.

#### 7.9.2 Filter compilation

The evaluator compiles each `Filter` case into a primitive sequence. The compilation table is internal to the evaluator and is sketched here for the contract: two conforming evaluators must produce equivalent results, which means they must agree on what each named filter means.

| Filter case | Compiled bitmap operation | Bitmap column |
|---|---|---|
| `.currentlyBelieve` | `(adj & 0xF) < 3` (threshold-compare on state field, value derived from § 6.1) | adjective |
| `.usedToBelieve` | `(adj & 0xF) >= 3 AND (adj & 0xF) < 7` | adjective |
| `.knewOnceAndErased` | `(adj & 0xF) >= 7` | adjective |
| `.state(s)` | `(adj & 0xF) == valueOf(s)` | adjective |
| `.trustworthy` | `((adj >> 12) & 0xF) < 4` (threshold derived from § 6.4) | adjective |
| `.trust(t)` | `((adj >> 12) & 0xF) == valueOf(t)` | adjective |
| `.sensitivityAtMost(s)` | `((adj >> 4) & 0xF) <= valueOf(s)` | adjective |
| `.userConfirmed` | `((prov >> 4) & 0x7) >= 2` (threshold derived from § 9.4) | provenance |
| `.captureChannel(c)` | `(op & 0xF) == valueOf(c)` (Drawer operational layout, § 5.6) | operational |
| `.hasFeatureFlag(f)` | `(op & maskOf(f)) != 0` (bitset test) | operational |
| `.inRoom(r)` | structured-tier index lookup | (none) |
| `.contentMatches(s)` | blob-tier scan | (none) |
| `.all(fs)`, `.any(fs)`, `.not(f)` | composed per Boolean algebra over child results | per child |

The `valueOf(...)` and `maskOf(...)` functions are derived from the bitmap layouts in §§ 5.5–5.7 and the manifest's `bitmap_layout_version`. They are pure functions of the layout; an evaluator that loads the layout from the manifest computes them automatically.

#### 7.9.3 Composite-bitmap evaluation

When a filter chain references multiple bitmap columns, the evaluator must compose the per-column results into a per-row Boolean. The composition rule:

1. Group the chain's bitmap-tier filters by `column-of(field)`.
2. For each column, fold the column's filters into a single composite predicate `P_column(bitmap) -> Bool`.
3. The row passes the bitmap-tier portion of the chain iff `P_adjective(adj) && P_operational(op) && P_provenance(prov)`.
4. Each `P_column` is itself executable as a single SIMD-aligned per-row instruction sequence.

When a filter chain references no fields in a particular column, that column's `P_column` is the constant `true` and is elided from the executed sequence.

The composite Boolean covers all 192 bits of the row's bitmap state in a single per-row evaluation. An implementation that evaluates columns sequentially with per-column short-circuiting is conforming; an implementation that evaluates columns in parallel via SIMD is also conforming.

#### 7.9.4 Filter ordering (mandatory)

The evaluator must execute filters in this order:

1. **Fingerprint pruning** (§ 11.5). Before any per-row scan, the evaluator tests the chain's bitmap-tier filters against the estate's per-wing fingerprints, then per-room fingerprints. Wings and rooms whose fingerprint cannot satisfy the chain are pruned before per-row evaluation. This is mandatory: an implementation that scans rows in pruned containers is non-conforming.
2. **Bitmap-tier filters per row.** All bitmap-tier filters execute next. Per-row cost is one per-column evaluation as in § 7.9.3.
3. **Structured-tier filters per row.** Filters reading the structured-row tier (`.inRoom`, `.lineageID`, `.createdAfter`, etc.) execute only on rows that survived the bitmap-tier scan.
4. **Blob-tier filters per row.** Filters reading blob/JSON tier (`.contentMatches`, `.nearVector`) execute only on rows that survived the structured-tier scan. Blob hydration happens lazily.

An evaluator is permitted to fold step 3 into step 2 when the structured-tier filter is sourced from an in-memory index (e.g., a room-ID hash table); the contract requires only that blob-tier reads not happen for rows pruned by earlier steps.

#### 7.9.5 Default filters

When `RecallFrame.filterChain` does not include a filter for the listed concern, the evaluator inserts the named default at the head of the chain:

- **Trust.** If no trust-related filter is present, prepend `.trustworthy`.
- **State.** If no state-related filter is present, prepend `.currentlyBelieve`.
- **Provenance.** If no provenance-confirmation filter is present, prepend `.userConfirmed`.
- **Access.** The evaluator prepends `.sensitivityAtMost(callerMaximum)`, where `callerMaximum` is determined by the caller's access claim (§ 9.2).
- **Tombstone exclusion.** Always: tombstoned rows are excluded. (Compiles to `(adj & 0xF) < 9` internally; the caller never writes this.)

Default insertion is part of the contract: an evaluator that does not insert these defaults is non-conforming. Callers that want to override defaults supply explicit filters for the relevant concern.

#### 7.9.6 Historical reconstruction

When `RecallFrame.asOf` is non-nil, the evaluator reconstructs each row's bitmap state at the supplied timestamp before evaluating filters (§ 6.8). Filters then apply to the reconstructed bitmap. Rows tombstoned after the supplied timestamp are visible; rows not yet captured at the supplied timestamp are not.

#### 7.9.7 Worked example

A caller invokes:

```swift
let stream = estate.recall(RecallFrame(
    filterChain: [
        .inRoom(RoomID("family/connie")),
        .currentlyBelieve,
        .trustworthy
    ],
    limit: 50,
    ordering: .byCaptureTimeDesc
))
```

No bit positions, no thresholds, no masks. The caller asks for currently-believed trustworthy rows in the family/connie room.

A conforming evaluator processes this internally as follows. The evaluator's bitmap operations are not visible to the caller and are not part of the public contract; they are shown here so implementers know what to build:

```
[Evaluator default insertion]
  filterChain += [
    .userConfirmed,                                  // § 9.4 default
    .sensitivityAtMost(callerMaximum)                // § 9.2 default
    // tombstone exclusion happens silently in the compiler
  ]

[Evaluator filter compilation]
  Per § 7.9.2, each named filter compiles to a bitmap operation
  using the layouts in §§ 5.5–5.7. The compiler produces:
    .currentlyBelieve         → (adj & 0xF) < 3
    .trustworthy              → ((adj >> 12) & 0xF) < 4
    .userConfirmed            → ((prov >> 4) & 0x7) >= 2
    .sensitivityAtMost(max)   → ((adj >> 4) & 0xF) <= valueOf(max)
    tombstone exclusion       → (adj & 0xF) < 9
  These integers come from the bitmap layouts and are derived,
  not authored by the caller.

[Step 1: fingerprint pruning]
  Compute the chain's bitmap-tier predicate over per-wing fingerprints.
  Wings whose bitmap fingerprints cannot satisfy the predicate are skipped.
  Within surviving wings, repeat at room level.

[Step 2: bitmap-tier per-row scan]
  For each candidate room:
    Compose per-column predicates from compiled operations:
      P_adj(adj)  = ((adj & 0xF) < 3)
                    && (((adj >> 12) & 0xF) < 4)
                    && (((adj >> 4) & 0xF) <= callerMaximumValue)
      P_prov(prov)= (((prov >> 4) & 0x7) >= 2)
      P_op(op)    = true (no operational filters; elided)
    For each row:
      pass = P_adj(row.adj) && P_prov(row.prov)

[Step 3: structured-tier filtering]
  .inRoom is enforced by the candidate-room iteration in step 2.

[Step 4: blob-tier filtering]
  No blob-tier filters in this chain. Skip.

[Ordering, pagination, hydration]
  Sort passing rows by capture_time descending.
  Apply limit: take first 50.
  Hydrate at .structured level (default).
  Return RecallStream.RecallPage.
```

The internal threshold integers (`< 3`, `< 4`, `>= 2`) are derived from the bitmap layouts in §§ 5.5–5.7 and the state-cluster topology in § 6.1. They are the evaluator's compilation output, not the caller's input.

Two conforming evaluators may differ in fingerprint-pruning aggressiveness, candidate-set materialization, and per-column composition strategy, but they must produce the same set of rows in the same order from the same named filter chain.

#### 7.9.8 Conformance hooks

A conforming evaluator passes a fixture suite covering:

- Each named filter case from § 7.9.1 with at least one test case verifying its compilation produces correct results against known fixtures.
- Filter chains spanning all three bitmap columns produce results equivalent to the canonical evaluation in § 7.9.7.
- Default-insertion behavior (a chain without a trust filter receives `.trustworthy`; a chain with explicit `.trust(.canonical)` does not).
- Fingerprint pruning verified by row-scan-count instrumentation.
- Historical reconstruction via `asOf` against a known audit trail.
- Tombstone exclusion across all chains.
- **Layout-leak test.** Public API surface scanned for raw bitmap field references, mask integers, or threshold integers in caller-supplied positions. Conforming implementations expose none.

These fixture requirements are part of § 13.

## 8. Error handling and failure modes

### 8.1 Error categories

| Category | Trigger | Caller response |
|---|---|---|
| `DisciplineViolation` | invariant breach (forbidden combination, illegal state transition, mutate of trust=verbatim to trust=proposed without expunge, expunge without confirmation) | do not retry; fix call |
| `SubstrateUnavailable` | backing store cannot be reached | retry with backoff |
| `ConflictMidFlight` | concurrent mutation invalidated caller's prior read | retry from a fresh read |
| `ManifestMismatch` | operation requires a manifest value not present | supply value or use different operation |
| `LatticeAnchorUnresolvable` | UDC code does not parse, or Wikidata Q-ID lookup fails after retries | supply alternative anchor or accept partial anchor |
| `TinyModelUnavailable` | operation requires a trained model the estate does not have | fall back to substrate-only scoring or wait for next training run |
| `PayloadShapeError` | verb frame slot has wrong type or missing required field | fix call |
| `BlobTierFailure` | blob-tier read failed (corruption, missing file) | structured and bitmap tiers still readable; surface as warning |

### 8.2 Mutation rejection rules

The `mutate` verb rejects:

- Any mutation that would produce `secret + public`.
- Any mutation that would change `trust=verbatim` to a non-verbatim value (use expunge-then-recapture).
- Any state transition not in the legal-transitions table (§ 6.2).
- Any mutation of a tombstoned row (§ 6.6 forbids resurrection).
- Any mutation of an audit row (only `expunge` may tombstone audit rows).

### 8.3 Recovery from partial failure

If a multi-row operation fails partway:

- Without an explicit transaction: rows mutated before the failure remain mutated. Caller may issue compensating `mutate` calls to restore prior state. Audit log records the partial success.
- Within an explicit transaction: all mutations roll back. Audit log records the rollback as a single audit row referencing the transaction.

### 8.4 Audit log integrity

Audit rows are append-only at the storage layer. An attempt to `UPDATE` or `DELETE` an audit row from outside the kit's API is rejected by storage-level constraints (in the SQLite reference implementation, via `BEFORE UPDATE` and `BEFORE DELETE` triggers). The only sanctioned mutation of audit rows is `expunge`-driven tombstoning.

## 9. Security, privacy, access, provenance

### 9.1 Access perimeter

The estate's contents are confined to its access perimeter. The perimeter is defined by:

- The estate's database files (resident on a specific device or storage volume).
- The estate's `owner_identifier` from the manifest.
- The estate's `access_posture` bitmap from the manifest.

An application accessing the estate must present credentials matching the owner_identifier. Cross-estate access is mediated by an access surface (ARIA_MCP) and is not the substrate's concern.

### 9.2 Sensitivity-tier access requirements

| Sensitivity | Access requirement |
|---|---|
| normal (0) | session-level access |
| elevated (4) | elevated access claim within session |
| restricted (8) | explicit per-row access grant |
| secret (12) | fresh authentication; single-row access; access claim does not persist |

The substrate enforces these requirements at the verb layer. `recall` calls without sufficient access skip rows whose sensitivity exceeds the caller's access claim. `mutate` calls without sufficient access fail with `DisciplineViolation`.

### 9.3 Exportability

A row's exportability bit determines whether it can leave the access perimeter:

| Value | Name | Behavior |
|---|---|---|
| 0 | private | stays inside the access perimeter |
| 8 | public | affirmative consent to leave the perimeter |

An access surface (ARIA_MCP, federation, export tools) must filter by `exportability = public` before any cross-perimeter transmission. The substrate does not transmit; export is the access surface's concern.

### 9.4 Provenance discipline

Every row's provenance bitmap is set at write time by the verb that creates it:

- `capture` sets `source_type` to one of `user_stated`, `observed`, or `external_doc` per the call's `channel` value, `confirmation` to `unconfirmed`, `confidence` to `unknown`.
- `propose` sets `source_type` to `model_inferred`, `confirmation` to `unconfirmed`, `confidence` per the proposing daemon's reported value.
- `learn` sets `source_type` to `external_doc` or `imported` per source-catalog entry, `confirmation` to `model_confirmed`, `confidence` to `medium-high`.
- `associate` sets `source_type` to `derived`, `confirmation` to `model_confirmed`, `confidence` per the association's signal-source weights.

Subsequent provenance changes go through `mutate_bitmap`, which writes an audit row.

Retrieval-layer code (in agents and in ARIA_MCP) must filter by provenance before treating any drawer as instruction. The substrate publishes a default filter `confirmation ≥ user_confirmed` for action-relevant content; agents may override but should record the override.

### 9.5 The `secret + public` exclusion

No row may simultaneously have `sensitivity = secret` AND `exportability = public`. The verb layer rejects writes that would produce the combination. The maintenance daemon scans for the combination periodically; on detection, it emits a discipline-violation proposal targeting the row.

## 10. Extensibility and versioning

### 10.1 State-extension flag

The state field of the adjective bitmap (§ 5.5, bits 0–3) admits 16 values; v1 uses 10. When state grows beyond 16 values, the state-extension flag at bit 16 of the adjective bitmap activates: when set, readers consult the row's operational bitmap for an extended state code that supplements the 4-bit base value.

The state-extension flag is specific to the state field. It is not a generic overflow mechanism for other adjective categories. Sensitivity, exportability, and trust have no equivalent flag; they are not at growth risk at v1 (sensitivity uses 4 of 16 values; exportability uses 2 of 16; trust uses 6 of 16, with all growth contained inside the gradient-ordered range).

State-extension flag activation rates are monitored by the kit; rates exceeding configurable thresholds emit warnings and recommend successor architectures (where field widths are wider).

### 10.2 Reserved bits

Every bit field reserves at least 30% of its value range for future growth. Reserved values are not used by v1 implementations and are guaranteed unused by current spec text. Future spec versions may assign reserved values; old readers must treat unknown values gracefully (typically by surfacing the row but not attempting to interpret the value).

### 10.3 Bitmap layout versioning

The `bitmap_layout_version` manifest key declares the layout version of the adjective bitmap. The `provenance_bitmap_version` key declares the provenance bitmap's layout version. Operational bitmap layouts are per-noun and versioned via the `operational_bitmap_layouts` manifest key (when present; absent means v1 defaults).

An implementation reading an estate must match the kit's expected layout against the manifest's declared layout version. Mismatches produce `ManifestMismatch` (§ 8.1).

### 10.4 Schema evolution

New noun shapes, new operational bitmap fields, new tunnel kinds, new source-catalog entries, and new verbs (the last forbidden by I-7) propagate through the manifest schema. New keys in the manifest are added; old keys are not removed. Old data continues to read correctly because old keys retain their semantics.

A breaking change to bitmap layouts produces a successor architecture (v2) and is out of scope for the v1 spec.

### 10.5 Adjective extensibility

The four adjective categories (state, trust, sensitivity, exportability) are constitutional and not extensible. New structural attributes find homes in:

- The operational bitmap of the relevant noun (per-noun structural attribute).
- Reserved bits of the adjective bitmap (cross-noun structural attribute, requires v1.x or later spec revision).
- The structured-row tier (variable-width attribute).
- The blob tier (open-ended attribute).

## 11. Operational model

The substrate's continuous-operation behavior is realized as a **standing-signals layer**. A standing signal is a long-running observer that reads from substrate state, external streams, or both; detects deltas against expected or historical patterns; and emits one of four output classes.

### 11.1 Four-emission-class contract

Every standing signal emits through one of four classes:

| Class | Effect | Discipline |
|---|---|---|
| `propose` | new candidate state requiring confirmation | row created with trust=proposed, state=pending |
| `associate` | Hebbian weight reinforcement on association graph | weight delta applied; signal_sources_seen bit set |
| mutate-candidate | proposed mutation of an existing row's bitmap | routed through `propose` for confirmation |
| diagnostic report | structured output the application can surface | not a verb call; surfaced via `signal_status()` |

No standing signal writes directly to bitmap state without going through the verb layer. The substrate's invariants (forbidden combinations, provenance discipline, audit recording) are maintained even under daemon activity.

### 11.2 The six v1 standing signals

| Signal | Reads from | Detects | Typical emission |
|---|---|---|---|
| Dreaming daemon | substrate blob/JSON tier + association graph | mining-pattern matches, novel structural alignments | `propose`, `associate` |
| Maintenance daemon | substrate bitmap tier (whole estate) | forbidden-combination violations, decay candidates, fingerprint drift, tombstone candidates | `propose`, diagnostic report |
| Training daemon | substrate audit log | enough new state transitions to warrant model update | model checkpoint, diagnostic report |
| Synchronization daemon | external streams (email, calendar, news) via foundation-model embedding | pattern matches against substrate, conflicts with substrate state | `propose`, diagnostic report |
| byReference validation signal | LearnedReference rows with `mode=byReference` | source returns 404, schema-incompatible response, content delta beyond drift threshold | `propose`, diagnostic report |
| Vector-similarity signal | substrate vector tier on schedule | pairs of rows whose embeddings have moved into similarity proximity | `associate` |

### 11.3 Scheduler

Standing signals share a scheduler. Each signal declares:

- **Trigger:** event-driven, interval-driven, or condition-driven.
- **Resource cost:** estimated CPU/memory/IO per run.
- **Freshness target:** how stale outputs may be before priority increases.
- **Concurrency policy:** whether multiple instances may run simultaneously.

The scheduler de-conflicts standing signals against caller-driven verbs (caller-driven calls have priority), batches compatible work, and emits backpressure when resource budgets are exceeded.

### 11.4 Standing-signals API

Applications access standing-signals output via three handles:

| Handle | Returns |
|---|---|
| `register_standing_signal(spec) -> SignalID` | adds a custom signal |
| `signal_status() -> [SignalReport]` | inspects what's running, queued, last emitted |
| `signal_subscribe(SignalID, callback)` | receives emissions asynchronously |

### 11.5 Cross-row reductions

The substrate maintains hierarchical fingerprints via field-wise OR-reduction of the three bitmap fields:

- **Per-room fingerprint.** The field-wise OR-reduction of every active row's adjective, operational, and provenance bitmaps within the room.
- **Per-wing fingerprint.** The field-wise OR-reduction of the wing's room fingerprints.
- **Per-estate fingerprint.** The field-wise OR-reduction of the estate's wing fingerprints.

A set-bit filter on any of the three fields can therefore prune a container whose OR for that field lacks the required bit. Threshold filters cannot prune through an OR, because the union of bits across rows does not bound any single row's field value.

The maintenance daemon updates fingerprints incrementally on capture and mutate. Fingerprint rebuilds on withdraw and expunge happen periodically rather than synchronously.

AND-reductions across all rows in a container produce "bits set in EVERY row" — uniform invariants. The maintenance daemon validates such invariants periodically.

The `popcount` of a room's adjective OR-reduction is the room's diversity score. The dreaming daemon uses diversity score to prioritize mining work.

### 11.6 Matrix layer

The substrate exposes a 16×16 binary matrix view of each row's three Int64 bitmaps. Rows of the matrix correspond to bitmap fields; columns correspond to bit positions within fields.

Matrix operations available:

| Operation | Returns | Cost |
|---|---|---|
| Row sum | popcount per field | O(16) |
| Column sum | bit-position dominance | O(16) |
| `M · M.T` | field correlation matrix | O(16³), hardware-accelerated |
| `M.T · M` | bit-position correlation matrix | O(16³) |
| `(M · M.T) - (M.T · M)` | asymmetry profile | O(16²) after the matmuls |

Cross-row matrix aggregation produces a population statistical profile. Sum across rows of M·M.T gives aggregate field correlation; aggregated asymmetry profile gives the population's non-normality signature.

## 12. Performance model and resource expectations

### 12.1 Per-row footprint

- 24 bytes per row in the bitmap tier (three Int64 columns).
- One million rows fits in 24 MB. Ten million in 240 MB. The bitmap tier is RAM-resident on commodity hardware for typical estate sizes.
- Structured-row tier varies; typical drawer adds 200–2000 bytes.
- Blob tier varies with content size.

### 12.2 SIMD lane fits

| Lane width | Fits | Use |
|---|---|---|
| NEON 64-bit | one Int64 column | per-column operations |
| NEON 128-bit | two Int64 columns | composite per-row operations |
| Metal SIMD 256-bit | full row matrix (256 bits) | matrix-layer per-row operations |

Hardware-accelerated paths target Apple Silicon (M1+); fallback paths use general int8 matmul.

### 12.3 Operator costs

Per-row costs for the five operator primitives are listed in § 7.7. Aggregate cost for a filter chain is the sum of its primitive costs, multiplied by the number of rows scanned. Fingerprint-pruned scans reduce row-count substantially: estate-level questions answer in one fingerprint test; wing-level in tens; room-level in hundreds.

### 12.4 Capture-path latency target

A capture-path P99 latency under 100 ms on Apple Silicon mobile devices (iPhone 13+) is the v1 target. Larger captures (multi-megabyte attachments) may exceed; the substrate accepts asynchronous capture for those cases.

### 12.5 Enrichment throughput target

Enrichment-daemon throughput target: at least 60 drawers/hour on Apple Silicon Mac (M1+), enriching all six rungs end-to-end. This admits overnight enrichment of a typical day's captures (~200–1000 drawers) with margin.

## 14. Examples and walkthroughs

### 14.1 Drawer lifecycle

A drawer captured, mutated, contested, resolved, and eventually superseded.

```
t=0   capture(content="call Connie about kids' summer plan",
              channel=typed,
              sensitivity=normal)
      → row R1 created
        adjective: state=active, trust=verbatim, sensitivity=normal, exportability=private
        provenance: source_type=user_stated, confirmation=unconfirmed, channel=direct_chat
        audit: A1 (initial capture)

t=1h  mutate(R1, kind=confirm)
      → R1 unchanged at adjective layer (already trust=verbatim)
        provenance: confirmation transitions unconfirmed → user_confirmed
        audit: A2 (provenance mutation)

t=2d  capture(content="actually summer plan is week of July 14, not July 7",
              channel=typed,
              sensitivity=normal,
              lineage_id=R1.lineage_id)
      → row R2 created with lineage_id matching R1
        adjective: state=active, trust=verbatim, sensitivity=normal, exportability=private
        provenance: source_type=user_stated, confirmation=unconfirmed, channel=direct_chat
        audit: A3 (initial capture of R2)

        Cascade per § 6.3:
        R1 transitions active → superseded
        Tunnel T1 (R2 → R1, kind=supersedes) created
        audit: A4 (R1 state transition), A5 (T1 created)

t=2d+1m  mutate(R2, kind=confirm)
      → R2 provenance: confirmation → user_confirmed
        audit: A6

t=30d  recall(at=t=1h, filter=lineage_id=R1.lineage_id)
      → returns R1 in state=active (its state at t=1h, before R2 existed)
```

### 14.2 Proposal lifecycle

A dreaming daemon proposes a tunnel between two drawers; the user confirms.

```
      Existing rows: R10 (drawer about kid A's swim lessons),
                     R11 (drawer about kid A's school sports day, dated three weeks earlier)

t=0   dreaming daemon detects mining-pattern match
      → propose(proposal_kind=new_tunnel,
                 target_object_type=tunnel,
                 payload={source: R10, target: R11, kind: references},
                 confirmation_source=human,
                 generated_by_class=dreaming_daemon)
      → row P1 created
        adjective: state=pending, trust=proposed, sensitivity=normal, exportability=private
        operational: proposal_kind=new_tunnel, target_object_type=tunnel,
                     confirmation_source=human, generated_by_class=dreaming_daemon
        audit: A1

t=1d  user reviews; mutate(P1, kind=confirm)
      → cascade per § 6.3:
        P1 transitions pending → active
        Tunnel T2 (R10 → R11, kind=references) created with trust=derived
        audit: A2 (P1 state transition), A3 (T2 created)
```

### 14.3 Recall query

A caller asks for currently-believed trustworthy drawers in a specific room, sorted by recency.

```swift
let stream = estate.recall(RecallFrame(
    filterChain: [
        .inRoom(RoomID("family/connie")),
        .currentlyBelieve,
        .trustworthy
    ],
    limit: 50,
    ordering: .byCaptureTimeDesc
))
```

The caller expresses intent in named filters. The evaluator (§ 7.9) compiles those filters to bitmap operations against the layouts in §§ 5.5–5.7, applies fingerprint pruning, then executes per-row evaluation:

1. Per-room fingerprint scan reduces the candidate row set to those in the room.
2. Compiled adjective-bitmap predicate AND-with-mask and threshold-compare per row (one per-column evaluation per row).
3. SIMD-ballot collects matching row IDs.
4. Structured-row tier hydrates the matched rows.
5. Ordering applied; limit applied; first page returned.

Full canonical evaluation is in § 7.9.7.

## 15. Compatibility and migration

### 15.1 Kit composition

A GeniusLocus is produced by composing kits:

- **LocusKit** — content + KG storage. Drawers, tunnels, KG facts, diary, manifest, audit.
- **VectorKit** — vectors. Embedding storage and nearest-neighbor query.
- **GeniusLocusKit** — LocusKit + VectorKit + CorpusKit + the Brain layer (standing-signals, matrix layer, training pipeline). Three internal storage tiers: structured-content-and-KG (LocusKit), vectors (VectorKit), RAG content-plus-vectors (CorpusKit).
- **CorpusKit** — the RAG kit. Content-plus-vector storage as a single bundle, providing the substrate's RAG tier. Required by GeniusLocusKit (which uses it as one of its three internal storage tiers); also usable standalone for RAG-only workloads.
- **ARIA_MCP** — MCP access surface. Composes one or more underlying kit configurations.

Applications use a kit; the kit owns its database files. There is no application-supplied substrate adapter.

### 15.2 Estate portability

Estates produced by one application are readable by any other application using the same kit version. The manifest is authoritative for the estate's configuration; bitmap layouts, lattice citation, owner identifier, framework profile values all live in the manifest.

### 15.3 Version migration

Migration between minor spec versions (v0.35 → v0.36, etc.):

- New manifest keys are added by the kit on first read of an old estate.
- New bitmap reserved bits remain unused; old data continues to read.
- New noun shapes appear as empty tables in old estates.
- New verbs (forbidden by I-7) do not occur within v1; v2 successor architecture handles new verbs.

Migration from v1 to v2 (when the 4-bit field width or another constitutional-adjacent constraint forces a successor architecture) is a separate spec exercise outside the scope of this document.

## Addendum A — OB1 technique integrations (v0.35.1)

The following additions were incorporated after the v0.35 spec was finalized,
based on a scope review of NateBJones-Projects/OB1 (Open Brain). All three
items ship in v1.0. None is deferred.

### A.1 — RecallTrace and RecallTraceItem nouns

Two new sidecar nouns are added to the substrate. They live in the LocusKit
content database as separate tables, not as rows in the drawers table. They
are not subject to the adjective/operational/provenance bitmap triple — they
are trace infrastructure, not content.

**RecallTrace** — one row per RecallStream invocation:

```swift
struct RecallTrace {
    let traceID: UUID           // primary key
    let estateID: UUID          // which estate was queried
    let query: String           // the RecallFrame query text
    let schemaVersion: String   // e.g. "geniuslocus.recall.v1"
    let responsePolicy: Data    // JSON: mmrLambda, bm25Weight, pageSize, active filters
    let createdAt: Date
}
```

**RecallTraceItem** — one row per drawer surfaced in any RecallStream page:

```swift
struct RecallTraceItem {
    let itemID: UUID
    let traceID: UUID           // FK → RecallTrace
    let drawerID: UUID          // FK → drawers (SET NULL on expunge)
    let rank: Int               // position in the page (1-indexed)
    let bm25Score: Float?       // nil if BM25 path not used
    let vectorSimilarity: Float?
    let rrfScore: Float?
    let mmrScore: Float?
    let returned: Bool          // false if filtered by write policy or sensitivity
    var used: Bool?             // nil until caller reports; true = acted on
    var ignoredReason: String?  // non-nil when used == false
    let createdAt: Date
}
```

**Schema:** Two `CREATE TABLE IF NOT EXISTS` statements in LocusKit's
DrawerStore. Idempotent migration via `CREATE TABLE IF NOT EXISTS` for fresh
databases and `ALTER TABLE` guards for upgrade.

**Trace emission:** `recall()` creates one RecallTrace row at invocation and
one RecallTraceItem row per drawer in every page it emits. The traceID is
returned to the caller in the RecallStream header.

**Usage reporting:** Callers report which items they acted on via:

```swift
public extension Estate {
    func reportRecallUsage(
        traceID: UUID,
        used: [UUID],                          // drawerIDs acted on
        ignored: [(UUID, reason: String)]      // drawerIDs passed over, with reason
    ) async throws
}
```

**Why this matters:** RecallTraceItem.used is the primary reward signal for
the dreaming daemon's learning cycle. It replaces the vague "recallPrecision
proxy" with a concrete measurement: what did the caller actually act on?
The dreaming daemon reads recent trace items (used == true → reward 1.0,
used == false → reward 0.0) alongside DiaryEntry.reward as its two-source
reward signal.

**Conformance addition (§ 13.2, item 17):** A conforming implementation
creates a RecallTrace row and at least one RecallTraceItem row for every
`recall()` invocation that returns a non-empty first page.

### A.2 — Write policy enforcement at the capture boundary

The `capture` verb enforces a content write policy before persisting. This
policy applies when the actor is `mcp_agent` or `substrate_daemon`. It is
advisory (warning only) when the actor is `user`.

**Blocked content categories:**

| Category | Definition | Threshold |
|---|---|---|
| Raw transcript | Verbatim AI session content not edited by the user | > 2000 characters |
| Reasoning dump | Internal chain-of-thought, scratchpad, or planning content | Any length |
| Secret | Content matching API key, token, password, or private key patterns | Any length |
| Oversized code block | Raw code block without accompanying summary | > 4000 characters (default, configurable) |

**Conforming content:** compact summaries, verbatim user-authored content,
decisions, lessons, constraints, open questions, artifact references, work
logs — anything the human intentionally put into the capture surface.

**The write policy does not restrict user-authored content.** Its purpose
is to prevent agent runtime write-back paths from bypassing human curation
by dumping raw agent output directly into the substrate.

**Behavioral invariant:** An actor with `actorClass == .mcp_agent` or
`.substrate_daemon` attempting to capture content in a blocked category
receives a `WriteViolation` error and the row is not written. The
`WritePolicyWarning` is emitted for user actors.

**Estate verb addition:**

```swift
// capture() now enforces write policy before persisting:
// - mcp_agent / substrate_daemon: throws WriteViolation if blocked
// - user: emits WritePolicyWarning, proceeds

public enum WriteViolation: Error {
    case rawTranscript(length: Int)
    case reasoningDump(indicators: [String])
    case secretDetected(pattern: String)
    case oversizedCode(length: Int, threshold: Int)
}
```

**Conformance addition (§ 13.2, item 18):** A conforming implementation
rejects a capture from an `mcp_agent` actor carrying raw transcript content
exceeding 2000 characters with `WriteViolation.rawTranscript`. The row must
not appear in subsequent recall results.

### A.3 — Versioned schema contracts for ARIA_MCP MCP tools

Every ARIA_MCP MCP tool call carries a `schema_version` string identifying
the contract version the caller is operating against.

**Version format:** `geniuslocus.<verb>.<major>` — for example:

| Tool | Schema version |
|---|---|
| recall | `geniuslocus.recall.v1` |
| capture | `geniuslocus.capture.v1` |
| propose | `geniuslocus.propose.v1` |
| writeback | `geniuslocus.writeback.v1` |

Tool calls without a `schema_version` are rejected with
`SchemaVersionRequired`. Tool calls with an unrecognized version are rejected
with `SchemaVersionUnknown`.

This is an ARIA_MCP-level contract, not a substrate-level contract. It lives
in the ARIA_MCP spec (not yet authored) as its first invariant. It is
documented here because it was identified during GeniusLocusKit architecture
review and must be carried into the ARIA_MCP spec when that document is
written.

**Strategic note:** This pattern directly enables future OB1 protocol
compatibility. An ARIA_MCP adapter implementing the
`openbrain.agent_memory.recall.v1` contract alongside
`geniuslocus.recall.v1` would make any GeniusLocusKit estate usable as an
OB1 memory backend — giving OB1 runtimes the structured recall, audit trail,
and dreaming daemon for free. This is a post-v1 opportunity; the contract
versioning discipline in v1 makes it possible without breaking changes.
